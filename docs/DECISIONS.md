# Decisions

One line each: decision, why, alternatives rejected. Newest at the bottom of each section.

## Foundation

- **Name stays LexBites.** Short, memorable, hints at "lexicon" and "bites". Rejected: Milon, WordBite (taken vibes).
- **Single package with `src/engine`, not a monorepo.** One build, one test runner, simpler CI; the engine is still a pure folder with no UI imports (enforced by lint-free imports and tests). Rejected: pnpm workspace with `packages/engine`.
- **Stable majors: Vite 7, TypeScript 5.9, Vitest 4, Tailwind 4, vite-plugin-pwa 1.3, React 19, React Router 7, Zustand 5, Dexie 4, ts-fsrs 5.** Known APIs, full peer compatibility. Rejected: Vite 8 and Vitest 5 (brand new, plugin-react 6 requires Rolldown pipeline).
- **Tailwind 4 with CSS tokens.** Theme colors are CSS variables (`--c-*`) so dark mode and per-user accent swap without rebuilding utilities. Rejected: Tailwind 3 config object.
- **Dark mode via `data-theme` attribute plus `prefers-color-scheme` fallback.** Supports auto, dark, light without a flash (inline script in `index.html`). Rejected: class strategy only.
- **Fonts self-hosted through Fontsource (Heebo variable for UI, Outfit variable for English display).** Offline-safe, no Google Fonts request. Rejected: system fonts only (English words deserve a display face).
- **BrowserRouter with `basename` from Vite `base` plus a `404.html` bounce.** Clean URLs on GitHub Pages; the service worker's navigate fallback handles deep links once installed. Rejected: HashRouter (ugly URLs in share cards and `/today`).
- **Deploy condition is "the repository default branch", not a hard-coded `main`.** The repo was empty, so the first pushed branch became the default; when the owner creates `main` and makes it default, deploys follow it with no workflow change.
- **Content build step copies and packs `content/` into `public/content/` at build time.** Keeps authoring files readable in git while shipping compact runtime JSON; `public/content` is generated and ignored.
- **Icons and splash screens are generated by `scripts/icons.ts` with sharp.** One SVG source, reproducible. Rejected: hand-made PNGs.
- **Playwright runs on the preinstalled Chromium locally and installs its own in CI.** The container pins an older browser build than the npm package expects.
- **GitHub Pages is enabled by the agent through the REST API.** The session's GitHub token has admin rights on the repo, so the one owner toggle was done automatically; `SETUP.md` keeps the manual fallback.

## Content

- **Inventory from wordfreq + WordNet, 62,000 lemmas.** wordfreq gives modern real-world frequency (subtitles, web, news), WordNet gives lemmatization, POS, sense counts, topics and derivational families. Inflections credit their base form; lexicalized forms ("tired", "building", "glasses") stay as their own lemmas too. Rejected: FrequencyWords (raw tokens, needs heavier lemmatization), spaCy (large model download for little gain).
- **CEFR signal from CEFR-J 1.5 (A1 to B2) and the Octanove C1/C2 profile.** Both open for commercial use with attribution. Rejected: Oxford 3000/5000 and English Profile (not open).
- **Exclusions from the LDNOOBW English list plus junk filters.** Removes slurs and obscenities; the list is downloaded at build time and never committed or printed.
- **Lemma ids are stable forever.** First build: id equals rank. Rebuilds keep existing ids and give new lemmas ids above the max, so user data keyed by lemma id survives inventory updates.
- **Topics come from the dominant WordNet sense only.** Using every sense mislabeled common words (for example "house" as work). Coverage is partial by design; Tier A authoring adds tags.
- **Tier A shards carry `forms` and an optional `context` paragraph.** `forms` lists irregular inflections so cloze blanking and validation work for "went", "children"; `context` serves the context mode of section 7.2.
- **Tier A authoring is parallelized across subagents, one shard file each, validated by `pnpm enrich --check`.** Same pipeline a future pass (or the API path) uses.

## Engine

- **Theta updates use the spec formula with per-answer weights (first exposure 0.25, review 0.06, probe 0.3) on top of K, plus a soft daily budget of 2 points.** The literal K of 2.0 per answer would move theta about 10 points on a good day; the owner asked for at most 1 to 2. Tests pin it.
- **Placement is a Bayesian grid estimate (0..100) with a steeper response curve, starting at d = 40 and probing the posterior mean.** Stops at 25 items or sd below 4 after 12. A failed meaning check lowers trust in self-report and turns on a check for every following item. Simulations at 20, 50, 80 land within 8 points in 90%+ of runs.
- **Assumed known = unstudied words below the new-word window.** Probes sample [theta - 20, theta - 4]; a passed probe becomes state `known` (no reviews), a failed one enters learning.
- **"I already know this" verified words enter FSRS with two Easy steps (a long first interval), not as `known`.** They are still checked eventually.
- **Selection boosts words with authored content (Tier A x3, Tier B x1.5) and orders families (root first, never two members of a family in one batch).**
- **Sessions: 3 slots per new word (intro, recognition 2 to 4 items later, typing production in the last third), max 5 new per session, reviews capped at half the session when new words are waiting.** Match pairs fold 5 mature reviews into one item. Typing rhythm and "end on a win" are enforced after layout.
- **Speed rounds rate wrong answers Hard, not Again.** The spec allows only Hard/Good there; a rushed miss should not wreck a card.
- **Streaks are derived from daily goal results every time (no stored counter).** Freezes are earned and spent during the derivation, so sync conflicts cannot corrupt the streak.

## App and data

- **One Dexie database for both profiles, rows keyed by user id.** The rival's synced rows live next to your own, so the rival card, league and read-only stats are plain local queries. Rejected: one database per profile (cross-profile views would need a second connection).
- **Answers are written in one transaction (word row, review log, profile) before the UI advances.** Progress is saved per item; the session plan position is persisted in `kv` so an interrupted session resumes.
- **Tier B words need two real dictionary example sentences or they are not shown.** No filler sentences: such words wait for Tier A authoring, and selection moves on to another candidate. Offline with nothing usable in the window, the session falls back to the nearest authored words so it is never empty.
- **Placement uses a dedicated, hand-checked bank of 363 words across the whole difficulty range (`content/placement.json`).** High-difficulty words are beyond Tier A, so the meaning checks need their own reliable Hebrew. Rejected: runtime translation during placement (slow, unreliable offline).
- **Curated items (phrasal verbs, idioms, collocations) get ids from 1,000,000 up, by list.** They never collide with lemma ids and stay stable as lists grow at the end.
- **Daily duel = 10 Tier A words with d 25..55 shuffled by a date seed.** Both phones compute the same list from the same bundled inventory; duels log reviews but never touch the learning queue.
- **Sync backend: Supabase over plain REST, no SDK.** Each table stores the row as JSON plus merge fields; a trigger enforces last-write-wins on `updated_at` and stamps `server_at` for incremental pulls. Access is gated by RLS comparing an `x-lexbites-key` header (sha256 of the shared passphrase) to the stored hash. Rejected: supabase-js (60 KB for four REST calls), Firebase (needs a Google project and SDK), Cloudflare KV (needs a Worker deploy step).
- **Project URL and anon key ship in the app (`src/sync/config.ts`); the passphrase never does.** The anon key is public by design and every table is closed by RLS without the passphrase hash, so committing it to a public repository is safe. Each phone types the passphrase once; only its hash is stored. Rejected: typing URL and key on each phone (error-prone on a phone keyboard).
- **Pulls re-read a two-minute overlap behind the cursor.** `server_at` is stamped inside the writing transaction, so a push that commits late can sit behind a cursor the other phone already passed; append-only rows (duel results, nudges) would then never arrive. Merging is idempotent, so the overlap costs only a few re-read rows.
- **React Compiler purity lint rule is off.** The app does not use the compiler; reading the clock in render is deliberate.
- **Sound effects are synthesized with WebAudio, no audio files.** Zero bytes to precache, off by default.
- **Share cards are drawn on a canvas and sent through the Web Share API (WhatsApp), with a PNG download fallback.**
- **FSRS personalization is a small on-device coordinate descent over 8 weights (initial stabilities and growth), accepted only if log loss improves by 1%+, from 400 reviews.** ts-fsrs ships no optimizer; the full Rust optimizer would be a large WASM download.

- **Push sender is a Supabase Edge Function, triggered by pg_cron (every 5 minutes) and by an `lb_events` insert trigger (nudges), not a GitHub Actions cron.** Nudges arrive within seconds even when the app is closed, and reminders land within 5 minutes of the chosen time; GitHub's scheduled workflows run late or get dropped under load. Rejected: the 0.3 GitHub Actions sender every 30 minutes (late nudges, a reminder window that a delayed run could miss), the rival's phone sending pushes directly (would need the VAPID private key in a public app).
- **The Edge Function holds no database credential.** Callers pass the passphrase hash (`x-lexbites-key`) and the function reads and writes through PostgREST with the anon key, so RLS limits it exactly like a phone; pg_cron and the trigger read the hash from `lb_config`. Rejected: the service role key (full access for a function that needs two tables).
- **Web Push implemented with WebCrypto, no library.** RFC 8291 encryption and RFC 8292 VAPID in about 200 lines that run unchanged in Deno, Node and browsers; tested against http_ece and node:crypto. Rejected: `npm:web-push` in Deno (relies on Node crypto APIs the edge runtime does not fully provide).
- **The owner adds two GitHub secrets (VAPID_PRIVATE_KEY, SUPABASE_ACCESS_TOKEN) and CI does the rest:** deploys the function, sets its secret, runs `supabase/push.sql` through the Management API, smoke-tests. A daily run deploys when the function is missing or outdated, so adding the secrets is enough. Rejected: asking the owner to deploy functions and run SQL by hand.
- **VAPID public key lives in the repo (`supabase/functions/_shared/keys.ts`), shared by the app and the function.** CI refuses to deploy a private key that does not match it. Rejected: a GitHub variable (a mismatch between build and server would break every subscription silently).
- **Reminder rules:** the daily reminder goes out once per local day at or after the chosen time (up to 3 hours late), only if the goal is not reached; the 20:00 streak alert only when a streak is alive and the goal is open; the two never arrive within the same hour, and a streak alert replaces a later daily reminder. Times use the phone's IANA zone, so the October daylight saving change needs nothing. Nudges older than 6 hours (a phone syncing late) are not pushed.
- **Supabase keepalive every 2 days from GitHub Actions, no secret.** `rpc/lb_keepalive` is a write that only stamps a time and is callable with the public anon key; the run also reads a table and calls `lb_authorized`. The same workflow re-enables scheduled workflows, which GitHub disables after 60 days without commits in public repositories.

- **No `Topic` header on pushes.** It is optional, Apple validates it strictly for real devices only, and the test push's 13-character topic was the one thing that set it apart while it failed on iPhone; the notification `tag` already replaces duplicates on the device. VAPID tokens are cached for up to 11 hours because Apple asks for at most one refresh per hour.
- **The push function keeps a public self-test (`GET ?probe=1`).** It sends Apple a message for a made-up device: Apple checks the token before the device, so `BadDeviceToken` for our token and `BadJwtToken` for a wrong-key control prove the server side without a phone. It writes nothing and reads nothing. The push server workflow runs it after each deploy.
- **Toasts: one at a time.** A repeated message or a new error replaces the one on screen; feedback to a tap shows at once and re-queues an interrupted announcement (nudges, weekly recap); announcements wait their turn. Rejected: plain replace (a "connected" toast wiped out a nudge on the same open), stacking (the owner saw errors pile up).
- **The update prompt applies updates itself.** It posts `SKIP_WAITING` to the waiting worker and reloads on `controllerchange`, with a fallback reload after 2.5 s. vite-plugin-pwa reloaded only for Workbox "update" takeovers, and on iPhone the waiting worker is usually found at launch ("external"), so the button did nothing visible.

## Recorded audio (0.8.0)

- **Every authored word, curated item and example sentence is pre-rendered with Kokoro (82M, Apache-2.0) at build time.** American `af_heart` (the highest-graded Kokoro voice) for words, items and sentences; British `bf_emma` (the best-graded British voice) for words and items only. With the accent on UK, sentences play the American recording. Rejected: system voices only (compact iPhone voices sound thin and vary per phone), Edge neural voices through `edge-tts` (unofficial endpoint, unclear terms), cloud TTS free tiers (need a card), in-browser neural TTS (a 300 MB model on the phone).
- **Context paragraphs (`context`, 5,797 of them, 1.26 M characters) are not recorded.** They would double the audio to about 1 GB and break the Pages limit; they keep the system voice. Revisit if the hosting changes.
- **A real slow version (Kokoro speed 0.75) of every word and item in both voices** plays on a long press. Long press on a sentence slows the recording by 0.75 with pitch kept, not a voice change. Rejected: stretched synthesis (robotic).
- **Pronunciation: misaki G2P (Kokoro's own) first; for heteronyms the lexicon reading that matches our IPA; then phonemes converted from our IPA (`scripts/audio/phonemes.py`), then espeak.** The candidates are tried in that order until a clip passes the checks. Heteronyms are found automatically (156 authored words have several readings in misaki's lexicon: read, lead, live, record, content...); the reading is chosen by comparing each to our IPA, so the British voice gets the same sense. Our 6,000 IPA strings all convert into Kokoro's alphabet; 77% match misaki exactly and 91% within one phoneme in ten. Rejected: our IPA for every word (Kokoro was trained on misaki's phonemes and sounds most natural with them).
- **Automated checks on every clip:** trimmed silence (60 ms lead, 150 ms tail), loudness normalized (voiced RMS -18 dBFS, peak at most -1 dBFS), duration bounds and the longest inner pause per kind. Whisper (faster-whisper, int8, CPU) listens to every word clip, normal and slow, and to a deterministic 10% sample of sentences (by key). `base.en` first; a miss goes to `small.en`, then `medium.en`, before it counts. A slow clip is sped back up (pitch kept) before Whisper hears it, since isolated slow speech is transcribed as syllables. A transcript counts as right when the words match, the letters match without spaces, or the phonemes are within 20% (homophones: "knight" for "night"; one phoneme for words of up to four); on a slow clip a trailing hesitation ("oh", "uh") next to the right word passes. After a miss the next pronunciation candidate is rendered; a slow clip that still misses gets one more try at 0.8 speed. Clips that fail the silence or duration checks are not published (the app falls back to the system voice). Numbers go to the job summary and `report.json` in the release. Rejected: no recognition check (27,000 clips nobody will listen to), one small model only (it mishears isolated words in the British voice far more than the bigger ones).
- **A slow clip that Whisper still cannot confirm after every retry is left out;** the app plays the confirmed normal clip at 0.75 speed (pitch kept) instead. Rejected: publishing it anyway (an unconfirmed clip on the very button meant for careful listening), stretched synthesis. Normal clips that miss after every candidate are published (the best candidate) and counted in the report: they are mostly isolated short words Whisper mishears, and the report button catches the real ones.
- **Words are rendered as a finished utterance (a final period after the phonemes).** It gives the falling citation-form ending; a bare word sometimes trailed off into an extra sound, worst in the British voice at slow speed.
- **AAC-LC, mono, 24 kHz, 48 kbps in `.m4a`.** Kokoro renders at 24 kHz, so nothing is lost; 48 kbps is clean on a phone speaker and every iPhone decodes it in hardware. Rejected: Opus (support in iOS Safari depends on the version), lower bitrates (ffmpeg's native AAC encoder is weakest there, and the total still fits Pages at 48 kbps).
- **Rendering runs in GitHub Actions (`.github/workflows/audio.yml`), 18 parallel jobs.** Free and unlimited for a public repository; 18 of the 20 concurrent job slots, so a site deploy never waits behind a render. A plan step hashes everything that shapes a clip (pipeline version, model, voice, speed, text, our IPA, overrides) and renders only hashes missing from the store, so new or edited content is rendered on the next push and nothing else. Pushes to the default branch that touch `content/shards`, `content/curated` or `scripts/audio` run it; other branches render an even 40-item sample of each kind and publish nothing, as a pipeline test. When it publishes, it starts the site deploy.
- **Hosting: a GitHub release named `audio-store` holds the files; the deploy copies them into GitHub Pages under `audio/`.** Nothing audio enters the git history, nothing needs the owner, and the clips are same-origin with the app (no CORS, Cache Storage works). The release holds word packs, sentence tars, the indexes and `store.json` (what each clip is and where it lives, for reuse). The deploy checks every index entry and ships without recordings rather than a broken index, and fails if the site would pass 990 MB. Rejected: a second repository with its own Pages site (needs the owner, two deploys to keep in step), committing audio (hundreds of MB in a public history), Hugging Face or Cloudflare R2 (an extra account; R2 needs a card).
- **Words ship as packs: one file per content shard and voice holding every clip of its words, normal and slow.** 33 packs per voice (30 shards and 3 curated lists) instead of 13,600 files, so precaching is a handful of requests. Sentences ship as one file each (`audio/s/<key>.m4a`), fetched on play. Clips are found by a hash of their text (`src/audio/key.ts`, shared by the build and the app), so the app needs no id mapping.
- **Playback decodes the clip (a slice of its cached pack, or the cached sentence file) and plays it through Web Audio (AudioBufferSourceNode), not an `<audio>` element (0.8.1).** An element made iOS open a "Now Playing" panel in the Dynamic Island for every word. Nothing streams from a URL, so it works offline in the home screen app. Rates other than 1 (speed slider, slow long press without a slow clip, slow sentences) are time-stretched in the app (WSOLA, `stretch.ts`) because a buffer source changes pitch with its rate. The AudioContext is resumed with a silent buffer on the first touches, and `navigator.audioSession.type = "playback"` (iOS 17+) keeps recordings audible with the silent switch on, as before. Dictionary audio from a server without CORS still uses an element (rare). 0.8.2: iOS leaves the context "suspended" or "interrupted" after calls, the lock screen or other audio, and `resume()` can hang; before every play it is resumed with a 600 ms limit and replaced once if still not running, it is also resumed on every tap and on return to the foreground, and a play whose clock does not move within 700 ms falls back to the system voice. Rejected: going back to an element (brings back the Now Playing panel). Rejected: keeping the element and clearing `navigator.mediaSession` metadata (iOS still shows the panel).
- **Offline: the word packs of the chosen accent are stored in Cache Storage in the background** (about 90 MB per accent, starting 5 seconds after launch, resumed when the phone comes online, redone on an accent change; `navigator.storage.persist()` is requested). Sentences are cached when played and prefetched for the session being built and the next one (the next likely new words and reviews due within a day); the sentence cache keeps the newest 3,000. Rejected: Workbox precache of the packs (it would hold up the service worker install for 90 MB).
- **The speed slider stays relative to its default for recordings.** At the default (0.95) recordings play as made; other values scale the playback rate (0.7 to 1.3, pitch kept). No settings migration needed.
- **"Report a problem" carries the clip.** The report stores what the user last heard for that word or its sentences (recording key and pack or file, voice, slow or not, or the system voice's name). `pnpm reports` lists them per word. A bad clip is fixed by adding phonemes for it in `scripts/audio/overrides.json` (`"us:word": "misaki phonemes"`): the hash changes and only that clip is rendered again.
- **System voices are ranked by quality from the voice URI** (premium, enhanced, standard, compact; macOS names and Edge/Chrome "Natural" voices are read too). Apple's novelty voices and the Eloquence voices are blocked by name, duplicates are merged into their best version, and settings show the best five for the accent, labeled. The list refreshes on `voiceschanged` (a voice downloaded while the app is open). The automatic choice is the best one; a saved choice that is no longer offered falls back to it.
- **The download guide for a better iPhone voice shows only on Apple devices with no enhanced or premium voice for the accent**, since recordings now cover all authored content and the system voice is only the fallback for free text.
- **Dictionary audio (runtime Tier B words) has its own cache rule, placed before the API rule, with range request support.** The app fetches it as a Blob when the server allows CORS and falls back to the element otherwise.

## Daily goal of 1000 XP (0.7.0)

- **Default daily goal 1000 XP, settings range 300 to 3000 in steps of 100, presets 500, 1000, 1500 and 2500.** With the spec XP values, combos and the new-word bonus a 20-item session earns about 300 to 500 XP, so 60 XP was met by the third answer and the ring, celebration and streak meant nothing. 1000 is two or three sessions, about 10 to 15 minutes. Rejected: lowering XP per answer (the spec fixes the values, and the owner asked for the goal to move).
- **Existing profiles move to 1000 through a one-time phone-side migration (`src/data/migrations.ts`), not a server change.** The app is local-first: a server-only change is overwritten by the next profile write from a phone. The migration runs at app start before the profile loads, changes only `settings.dailyGoal` and records itself twice: a `kv` flag (once per phone) and `profile.migrations['goal-1000']` (once per profile, synced with the row). Rejected: a flag per phone only (the other phone, updating later with an old copy, would migrate again over a manual change); a schema version bump (the change is in a JSON field, no index changes).
- **The migrated row is stamped `updatedAt + 1`, not now.** If the phone holds a current copy, the migrated row is the newest and syncs up. If it holds a stale copy of a profile that was already migrated and then changed by hand elsewhere, the server's newer row wins last-write-wins and comes back on the next pull. Pinned by a two-phone sync test. The same rule was used for the direct server update, so a phone write landing at the same moment is never overwritten.
- **Both profiles on a phone are migrated, the rival's copy too.** The rival's phone may update later; until then the rival card shows the right goal, and if the rival's own phone has a newer row, it wins. A phone with no copy of a profile leaves it to that profile's own phone; new profiles are created migrated.
- **A day met under the old goal stays met.** `goalReached` was already sticky for the day; home and the today screen now read it, so a day met at 60 XP shows as done (full ring) after the goal rises, and the streak keeps counting it. Daily rows are never rewritten. Rejected: recomputing today against 1000 (would break a streak the user already secured).
- **Levels rescaled: level n starts at 1000 × (n-1)^1.55.** The old base of 60 was one goal day under the old goal, but real days earn hundreds of XP, so the 16 titles (one per 3 levels) were used up in about a month. With the base at one 1000 XP day: level 2 after day one, level 10 after about a month, level 46 (the last title) after about a year. Levels are derived from total XP, so nothing is stored or migrated; the shown level drops once, and no level-down message is shown. Rejected: keeping the curve (titles meaningless after a month).
- **XP badges 10,000 and 50,000 kept, 250,000 added.** At 1000 a day they are 10 and 50 goal days (the second lines up with the 50 active days badge); 250,000 gives a long-term target. Goal and streak badges count days, so they are unaffected.
- **Push copy says what is left instead of "five minutes".** The function reads each user's goal from `lb_users` (`data->settings->dailyGoal`) and today's XP, and says "עוד 400 XP ליעד של היום. סשן אחד וזה סגור" (sessions estimated at 400 XP each). Without a goal on the server it falls back to "סשן או שניים". The 20:00 rule itself is unchanged.
- **The rival card shows the rival's goal progress** (a thin bar and "/ 1000 XP", ✓ when met), read from the rival's synced profile. The weekly league compares XP only and has no goal.

## Sessions after the daily cap (0.6.0)

- **Root cause of the owner's "one word per session" report:** the learn composer took only due reviews (`due.slice`) and its top-up with not-yet-due words ran for review and boss sessions only (`mode !== 'learn'`). Once the day's new words were in and the queue was empty, the plan held nothing but the sanity probe: a 1-item session, every time.
- **A learn, review or boss session is filled to its normal size, in this order:** due reviews (oldest first), early reviews of words not touched today (lowest FSRS retrievability first), the hard-words pool among words reviewed today (leeches, then lowest stability), practice of words learned today (weakest first), then repeats of the same words in other exercise types (at most 5 appearances per word, never twice in a row). A probe alone is never a session. Rejected: lifting the cap automatically (the cap protects the review load, and the owner wants slow, steady growth).
- **Early reviews go through FSRS normally.** ts-fsrs computes the stability gain from the real elapsed time and retrievability, so a near-certain recall barely moves stability and, in every case measured, the next due date only moves later (for example: S 20 reviewed after 1 day becomes about 24; same-day practice of a word learned today leaves S unchanged). One guard: no Easy on a word that was not due (capped at Good), because the Easy bonus on top of an early review overshoots. Early answers carry `early: true` in the review log and are left out of the 7-day retention that drives cap suggestions, which they would flatter. Rejected: practice that does not schedule (a forgotten word must still lapse) and a separate review purpose (would need sync and rebuild changes for no gain).
- **Theta is untouched by the fill:** early and repeated items are reviews (weight 0.06) inside the existing 2-point daily budget, so playing more never speeds up the level.
- **"עוד 5 מילים חדשות": one tap raises today's cap by 5, for today only.** Stored as `bonusNew` on today's daily stats row (synced as part of the row, no schema change), shown on home, at the end of a session and on an empty learn screen once the cap is reached. The setting itself never changes. Rejected: a settings change (it would stick) and a confirmation dialog (one tap was asked for).
- **Short sessions with new words:** when there are few learned words (a brand-new user with the minimum cap of 3), each new word gets up to 3 extra practice items (listening, Hebrew to English, cloze) after its recognition check, so the first session is not 10 items long.
- **Optional modes need a minimum pool of learned words:** hard words and listening 3, speed round 4, boss 30 (previously counted from all word rows, including ignored and passed probes). Small pools repeat in other exercise types to reach a normal length; below the minimum the button is disabled and the session screen explains why, with a button to a learning session (and the cap option when it applies). Speed rounds never show the same word twice in a row.

## RTL and bidi (0.5.0)

- **One bidi rule set, one file, used everywhere** (`supabase/functions/_shared/bidi.ts`, imported by the app through `src/i18n/bidi.ts` and by the push function). An LTR run is a stretch without Hebrew that starts and ends with a Latin letter or digit, may hold spaces and ASCII punctuation, and may start with a sign (+3, −0.4, ×2, ~25). Runs with a Latin letter or a sign are isolated; plain numbers are left alone (they already render correctly in Hebrew). Rejected: fixing strings one by one (the owner kept finding new ones).
- **Plain text uses LRM/RLM marks, never the Unicode isolate characters (LRI, RLI, FSI, PDI).** WebKit, which draws every page, canvas and notification on the iPhone, does not implement the isolates (WebKit bug 130823), while LRM/RLM work in every engine. Each LTR run is wrapped as LRM…LRM; a Hebrew string that would start with an LTR run gets a leading RLM; push notifications, canvas text and other plain-text Hebrew always start with an RLM.
- **In the DOM, isolation is CSS on an element with `dir`** (`<Ltr>`: `dir="ltr"`, `unicode-bidi: isolate`; `<He>`: an explicit RTL paragraph whose LTR runs are each rendered as `<Ltr>`). Hebrew content (translations, sentence translations, memory hooks, confusable explanations and tips, placement options, toasts) renders through `<He>`. Rejected: `dir="auto"` with `unicode-bidi: plaintext` for Hebrew text: 1,388 of 1,587 memory hooks and 83 of 120 confusable explanations start with an English word, which turned the whole paragraph LTR.
- **A Hebrew prefix stays with the English word it is attached to** ("מ-LexBites", "ב־40 XP", "ל-Safari"): one to three Hebrew letters plus a hyphen or maqaf right before a run are kept on the same line (a `nowrap` span in the DOM, a word joiner U+2060 in plain text), and the run is isolated so the prefix stays on its right.
- **All UI strings pass through the helper once, at the source** (`bidiStrings()` over the table in `src/i18n/he.ts`, including every string a function there returns), so React text, toasts, aria labels and canvas text get the same treatment. Inline Hebrew with English or digits outside `he.ts` is a test failure (`scripts/bidi-scan.test.ts`).
- **Regression tests check what the eye sees.** `src/i18n/bidi.test.ts` runs every UI string (functions sampled with typed arguments) and every push notification through a reference Unicode Bidirectional Algorithm (bidi-js) and asserts each LTR run is drawn whole and in order and each Hebrew line resolves RTL. bidi-js counts UTF-16 code units, so the test helper stands a neutral symbol in for each emoji.
- **English blocks are `dir="ltr"` block elements, left aligned** (sentences, definitions, cloze sentences), not inline LTR spans inside an RTL paragraph, which right-aligned wrapped English lines. Direction and alignment rules sit in Tailwind's base layer so utilities such as `text-center` still win; before, the unlayered `.en { text-align: left }` silently overrode `text-center` on English elements.
- **Time runs right to left on every chart** (minutes per day, forecast, retention, heatmap, level over time, the weekly league), matching the RTL layout; the heatmap scrolls to the current week. Rejected: mixed directions (three charts ran left to right, two right to left). Score pairs read in the same order as the players above them (mine on the right).
- **Search fields:** the library and confusables search fields are RTL while empty (the Hebrew placeholder reads correctly) and `dir="auto"` once typed; the confusables search also matches the Hebrew explanation. The typing exercise, the passphrase and the server fields stay LTR.
- **The bidi test page (`/dev/bidi`) is reachable in production by URL** (linked from settings in dev builds): every UI string that mixes directions, Hebrew content with English, every push notification as plain text, both share cards and the inputs. Its string list is a committed JSON (`src/i18n/bidi-catalog.json`) because minified code has no parameter names to sample functions with; the test rewrites it locally and fails in CI when it is stale.

## Texts (0.9.0)

- **Read mode cards use a light lookup, not the session enrichment.** Sessions still need Hebrew plus two real example sentences (spec 1), so `enrich()` keeps that rule; a card only needs Hebrew, so `lookup()` asks the dictionary and the translator in parallel and needs only a translation. Lookups are cached in IndexedDB (`glossCache`); failures are never cached, so retry always asks again. Rejected: relaxing `usable()` (sessions would show words with no examples).
- **Google's public gtx endpoint is the first translator, MyMemory the fallback.** It answers single words and long texts, allows CORS and has no small daily quota; MyMemory's anonymous quota (and its cached "quota exceeded" warnings) made it the weak link. Whole texts are translated in batches of about 1,500 characters joined by newlines, and every sentence translation is cached (`translations`). Rejected: a paid API (spec 0.9).
- **Names and brands are detected per text, without a name list for everything:** a word with capitals after its first letter (OpenAI, GPU), a capitalized word mid-sentence that the same text never writes in lower case, a sentence-initial word that the text capitalizes elsewhere mid-sentence, plus a short list of brands that are also English words (Anthropic, Meta, Mistral, Apple...) when capitalized. Cost: days and months mid-sentence are not marked, which is fine (they are basic words).
- **Marks are stored with the text** (auto-marked at save: level − 4 and up, not studied, hardest first, at most 60), then edited by hand. They do not move when the level changes, so the list stays what the user curated.
- **Words added from a text get session content built from the text:** the lookup's Hebrew, the text's own sentences with their translations, then dictionary examples. In a text practice the text's sentences replace the authored ones, so every cloze and intro shows the text.
- **Text practice is a session mode (`text`)** run by the normal runner, so answers schedule FSRS like any other. Up to 10 words: new words get intro, recognition, cloze and typing; words already in learning get a cloze and a recall check. Practiced words go first among due and fill reviews in learn and review sessions for 4 days (`priority:<user>` in kv).
- **The comprehension check is built from the text itself, without AI** (no paid service, works with any text): pick the Hebrew meaning of a sentence, pick the sentence that says a Hebrew line, pick what comes next. Prompts are spread across the text. Rejected: LLM-written questions (needs a paid key).
- **Articles from a link go through the free Jina reader (`r.jina.ai`, no key)**, because most news sites block cross-origin reads from a web app; a direct fetch with paragraph extraction is the fallback, and pasting always works.
- **Texts are local and travel in export/import, not in sync.** They are personal reading material; syncing them would need a new table on the server for little gain. `/read` redirects to `/texts`.

## Audio that never goes silent (0.10.1)

Reported: sometimes the app plays nothing at all (no words, no sentences), not a volume problem; closing the app and opening it again brings the sound back. So the state that broke lived for the life of the page.

- **Every step that can hang on iOS has a deadline and falls through to the next source** (`src/audio/speech.ts`): the recording lookup (4 s for words, 5 s for sentences: Cache Storage and fetch can stay unsettled after the background), the generated clip (3 s), `decodeAudioData` (4 s; Safari can leave it pending after an interruption), the dictionary fetch (4 s) and an element's `play()` (3 s). Before, one hung promise left the speaker pulsing and every later tap waiting on the same broken state.
- **The AudioContext is replaced inside the next tap whenever it may have gone silent:** the app went to the background (`visibilitychange`, `pagehide`), iOS moved it out of "running" by itself, a play did not start or decode, or it has been idle for two minutes. iOS can bring a context back "running", with its clock moving, while nothing comes out of the speaker; the app cannot detect that, and a context created inside a gesture is the only reliable cure (it is what restarting the app did). The capture listeners on `pointerdown`, `touchend` and `click` make every tap such a gesture. Rejected: a new context for every play (a play after a lookup is outside the gesture, so iOS would start it suspended).
- **Speech synthesis is resumed and flushed before every utterance, and retried once if it does not start within 3 seconds.** iOS can leave it paused after the background or a call, with every new utterance queued silently behind it. On return to the foreground the queue is flushed too. It is primed again in the next tap after the context went stale.
- **A newer play supersedes one still looking up its clip** (a play id bumped by every play and by stop): a late lookup never plays over the next word, and stop in "play all" also cancels a lookup in flight.
- **Sound effects share the words' context** instead of a second one, so iOS has one context to keep alive and it is replaced with the rest.
- **The recordings root index has a 5-second network limit and is fetched again when it could not be read**, instead of caching the failure (a weak connection at start meant the system voice for the whole session).

## Text audio and texts review (0.10.0)

- **Texts get the recordings' voice, rendered on GitHub Actions, not on the phone.** Measured here: Kokoro (int8 or fp32) in WebAssembly runs 2 to 3 times slower than real time even with 4 threads (a 3-minute article would take 6 to 9 minutes with the screen on, and iOS stops it in the background); natively on 4 cores it runs 3.4 times faster than real time. So `scripts/tts/render.py` reuses the recordings pipeline (`scripts/audio/generate.py`: Kokoro v1.0, misaki G2P with the espeak fallback, af_heart for sentences, the accent's voice for words, the same loudness and checks, AAC 48 kbps) in `.github/workflows/tts.yml`. Rejected: Kokoro in the browser (too slow, 100 MB download, memory risk in a home screen app); Hugging Face Spaces or other hosted TTS (needs an account, sleeps, third-party quota); the system voice (the owner's complaint).
- **Delivery through Supabase, behind the sync passphrase** (`supabase/tts.sql`): phones add a job (the units of the text that have no recording, in reading order) to `lb_tts_jobs`; the workflow writes base64 m4a clips to `lb_tts_clips` four at a time and updates the job's progress; phones download each clip as it lands into Cache Storage (`src/audio/generated.ts`), so a text starts playing before it is finished and plays offline afterwards. Only the service role changes jobs or writes clips; the workflow reads that key through the Management API with the existing `SUPABASE_ACCESS_TOKEN` and masks it. Clips are deleted after 120 days, jobs after 30.
- **Starting the render: the lexbites-tts Edge Function dispatches the workflow** when it has a fine-grained token with Actions write on this repository (`TTS_DISPATCH_TOKEN`, SETUP.md step 7); it first checks the passphrase hash through row-level security (the job must be readable with it). Without the token the workflow's five-minute schedule picks jobs up (idle runs end in seconds), so nothing waits on the owner. A run lingers 150 seconds after its last job to catch the next text without a cold start. Rejected: a permanently running worker on Actions (against GitHub's terms).
- **The texts are private, the repository and its Actions logs are public:** the dispatch carries no text, `render.py` prints counts and timings only, library messages go to a file that is only counted, and errors print their type only.
- **Playback order everywhere:** recording, then a generated clip, then (words only) the dictionary clip, then the system voice. While a clip is on its way the speaker shows "preparing" and plays nothing (`src/audio/pending.ts`); "play all" waits for each sentence. The system voice plays only when rendering failed, is stuck for 20 minutes, or cannot start (sync off), and the text says so with a retry. Polling runs in the background on every screen and resumes at app start.
- **Why recorded words and sentences still sounded robotic in 0.9:** pasted sentences are never in the recorded set, the 0.9.0 practice session replaced the authored (recorded) example sentences with the text's own, and on a cold start the word index could miss its 1.5-second deadline. The text screen now warms the indexes and the deadline is 3 seconds.
- **Sheets follow the visual viewport** (`src/ui/viewport.ts`): on iOS the keyboard shrinks only the visual viewport, so a sheet pinned to the bottom slid under it with its button. The overlay now covers `--vv-top`/`--vv-h`, the panel scrolls inside, and the main action sits in an always-visible footer; while the keyboard is up the bottom safe-area padding is 0; when it closes the page is scrolled back (WebKit can leave it offset, which hid content under the tab bar). Scroll panes get `min-h-0` (old Safari flexbox bug).
- **Only words to learn are highlighted.** The green underline of words already in learning meant nothing to the owner and is gone; in the list a learned word gets a check mark.
- **No title field.** A short title is made from the text (a headline-like first line, else the first clause, at most six words) or taken from a fetched article, and can be renamed later (pencil next to the title). A link pasted into the text box is fetched as an article.
- **The most frequent 400 words are never marked**, whatever the level (a low placement marked "the" and "with"). The comprehension check uses sentences of at most 28 words so its answers stay readable, and English answers are left aligned.

## Hardening

- **Theme-aware accent colors.** Light mode uses deeper coral (#c63f17) and violet (#6a48f0) with white text; dark mode keeps the bright coral (#ff6b4a) and a lighter violet (#9b82ff) with dark text on buttons. Every text and button pair passes WCAG AA (Lighthouse accessibility 100). Rejected: one bright accent everywhere (2.8:1 on white).
- **Pinch zoom allowed.** `maximum-scale=1` was removed from the viewport (accessibility); inputs are 16px and `touch-action: manipulation` still prevents the iOS focus zoom and double-tap zoom.
- **Secondary screens are lazy-loaded.** Initial JS dropped from 126 KB to 99 KB gzipped; all chunks are precached so offline navigation stays instant.
- **robots.txt disallows indexing.** A private two-person app; the SEO score is irrelevant by design.

## Section 7.3 ideas

- **Read mode and word list import: shipped together (`/read`).** Paste any English text; words new at the user's level are highlighted, tap for a quick card, add one or up to 25 at once. A pasted word list is just a text. Rule-based lemmatization with an irregular-forms table keeps it offline and instant.
- **Confusable pairs: shipped as authored "explain the difference" cards** (`content/confusables.json`), focused on confusions typical for Hebrew speakers.
- **Weekly boss review: shipped** (30 mixed items, badge).
- **Synonym/antonym mini-exercises: deferred (B-003).** They need authored synonym sets per C1 word to avoid ambiguous answers; revisit after Tier A reaches C1 ranks.
- **Pronunciation self-check: deferred (B-004).** Safari's SpeechRecognition support is partial and unreliable in standalone mode.
- **Non-teachable inventory entries are skipped, not deleted.** About 3% of authored entries turned out to be inflected forms, first names or spelling variants. Deleting them would shift ranks and therefore shard membership, so the build derives a skip list from their Tier A definitions; they keep their cards but are never introduced, probed, offered as distractors or used in duels. Abbreviations ("info", "lab") stay teachable.
